# 企业大脑原始资料追溯规范

## 1. 目标

企业大脑中的每一条业务事实，都必须能追溯到用户最初提供的资料，而不是追溯到数据库表、记录 ID 或 AI 抽取任务。

一条完整的业务来源至少包含：

1. 原始文件名与可访问的文件版本。
2. 人能理解的定位，例如 PDF 页码、Word 标题与段落、表格工作表与单元格、图片编号或音视频时间码。
3. 与当前事实对应的原文摘录。
4. 文件版本、内容哈希和上传时间，用于判断资料是否已经变化。

`brand_profile`、`knowledge_documents`、`kb_entries` 和 `kb_chunks` 等数据库位置只能用于系统处理和排查，不能展示为业务来源。

## 2. 当前数据缺口

- `brand_profile` 保存了抽取后的品牌事实，但没有关联原始文档。
- 部分 `knowledge_documents` 保存了标题与抽取正文，但 `asset_url` 为空。
- `kb_entries.file_url` 可以关联部分文件，但现有切片只有内部序号，无法稳定表示页码、章节或段落。
- 因此当前只能证明“系统里曾经有这条抽取结果”，不能证明“这条事实来自用户哪份原始资料的哪一段”。

存量数据缺少原件或定位时，必须显示“待补录”，不得显示“可追溯”，也不得进入正式版本。

## 3. 推荐数据模型

### source_documents：用户上传的原始资料

- `id`
- `org_id`
- `original_filename`
- `storage_url`
- `mime_type`
- `file_hash`
- `version_no`
- `uploaded_at`
- `uploaded_by`
- `supersedes_document_id`

原始文件一经入库不得被同名文件静默覆盖。新文件应生成新版本，并保留版本关系。

### source_blocks：可引用的原文内容块

- `id`
- `document_id`
- `block_index`
- `locator_type`
- `locator_label`
- `page_number`
- `section_path`
- `paragraph_index`
- `sheet_name`
- `cell_range`
- `time_start_ms`
- `time_end_ms`
- `original_text`
- `text_hash`

`locator_label` 是给业务用户看的定位，例如“第 6 页｜三大承诺｜第 2 段”或“报价表｜基础配置!B12:F18”。内部 chunk 序号不能替代它。

### knowledge_facts：企业大脑中的结构化事实

- `id`
- `org_id`
- `module_code`
- `fact_key`
- `fact_value`
- `status`
- `active_version`
- `created_at`
- `updated_at`

事实可以由 AI 抽取、融合或人工编辑，但来源关系必须单独保存。

### fact_evidence_links：事实与原文之间的证据关系

- `id`
- `fact_id`
- `source_block_id`
- `relation_type`
- `support_scope`
- `is_primary`
- `created_by`
- `created_at`

一个事实可以有多份证据；同一原文也可以支持多个事实。融合结果必须保留每个候选事实与对应原文的关系。

## 4. 上传与写入流程

1. 用户上传文件后，先写入 `source_documents`，保存原文件、哈希和版本。
2. 解析器按文件类型生成 `source_blocks`，同时保存原文和可读定位。
3. AI 从内容块抽取候选事实，写入 `knowledge_facts`。
4. 每个候选事实必须同时写入 `fact_evidence_links`，不能先写事实、以后再猜来源。
5. 多份文档描述同一模块时，分别保留候选事实和证据，再生成一个带完整证据集合的融合候选。
6. 用户选择、修改或确认事实时，只改变生效状态，不删除历史候选及其证据。
7. 原文件更新后，基于哈希判断受影响的内容块和事实，生成新版本并提示复核。

## 5. 用户界面规则

- 来源区标题统一为“原始资料依据”。
- 第一行展示原始文件名和版本，而不是表名或内部标题。
- 第二行展示页码、章节、段落、单元格或时间码。
- 第三行展示支持当前事实的原文摘录。
- 可以补充“当前抽取条目”帮助管理员排查，但不能把它称为来源。
- 原件和定位均存在时显示“出处完整”。
- 有原件、缺定位时显示“待补段落定位”。
- 缺原件时显示“待补录原件”。

## 6. 冲突与融合

当多份资料对同一事实给出不同答案时，界面应按候选项并列展示：事实内容、原始文件、具体位置、原文摘录和版本日期。AI 融合结果必须说明引用了哪些候选项，不能生成一个失去出处的新答案。

用户选择某一业务口径后，其余候选仍作为历史证据保留。若选择“AI 融合”，应建立到全部被采用内容块的证据关系。

## 7. 发布门禁

正式发布前逐条检查：

- 是否关联原始文件；
- 是否有稳定、可读的原文定位；
- 原文摘录是否仍与文件哈希对应；
- 冲突是否已由用户确认；
- 事实是否仍在适用时间和业务范围内。

任一必需证据缺失时，该事实只能保存为草稿或“待补录”，不能标记为正式可用。

## 8. 落地顺序

1. 先建立四张证据模型表及访问权限。
2. 改造上传解析流程，使新资料从第一天起具备段落级出处。
3. 对存量资料运行回填任务；能重新找到原文件的自动匹配，不能匹配的进入人工补录队列。
4. 将对话机器人、视频脚本和召回内容的知识读取统一改为只使用通过发布门禁的事实版本。
